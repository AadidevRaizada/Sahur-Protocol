## Diagram vs build differences (how to handle)

The diagrams stay exactly as drawn. Where they differ from the real build, treat it the way a design review would: a short, neutral **"Model review"** sub-section (or `::: patch title="MODEL REVIEW"`) near the end of the chapter that lists each difference and what the build actually does / how the model would be revised. Never call the earlier lab work "wrong" or mention "earlier drafts"; phrase it as findings of reviewing the model against the implementation (a normal SE activity — verification). Examples:
- Use case: *Exit Game* has no in-game button (the browser tab is closed); *View Story* is a static premise pane, cutscenes are watched only inside a run; *Save Progress* is automatic (checkpoints), so it is an «include» of room start / upgrade pick / pause rather than an actor-started use case; boss rooms give a one-card **Signal Roll** rather than three upgrade cards; there is no overwrite warning on WAKE UP.
- Activity: the *Room Type?* decision with a *Choose a Relic* branch corresponds to the real flow combat room → upgrade pick (the game's word is "upgrade/skill"; "relic" survives only as the internal array name `state.relics`); HP is checked on every hit, not once per room; boss rooms exist per biome before the Bubble.
- Class: the code has **no classes** (data tables + plain objects + functions); the class diagram is a **conceptual/domain model**. Include a mapping table (lab class → real construct) from fact sheet §13. *Boss* is a generalisation of *Enemy* only conceptually; in code it is a separate object sharing `damageEnemy()` via duck typing. Mention what the model leaves out (cutscene system, input/touch, particles).
- Sequence: map each lifeline to real functions (fact sheet §13 Exp 6 table). Saves happen at room start, upgrade pick, challenge, biome change, pause, main menu, final-boss start; victory deletes the save; game over keeps it.
