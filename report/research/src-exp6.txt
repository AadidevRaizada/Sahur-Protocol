Theory:
What is Behavioral modeling?
All behavioural models really do is describe the control structure of a system. This can be things like:
Sequence of operations
Object states
and Object interactions
Furthermore, this modelling layer can also be called Dynamic Modelling. The activity of creating a behavioural model is commonly known as behavioural modelling. As well as this, a system should also only have one behavioural model – much like functional modelling.
Two types of behavioral model are:
Data processing models that show how data is processed as it moves through the system;
State machine models that show the systems response to events.
These models show different perspectives so both of them are required to describe the system’s behavior.
How to draw Sequence diagrams?
A sequence diagram is a kind of interaction diagram that shows how processes operate with one another and in what order. It is a construct of a Message Sequence Chart. A sequence diagram shows object interactions arranged in time sequence. It depicts the objects and classes involved in the scenario and the sequence of messages exchanged between the objects needed to carry out the functionality of the scenario. Sequence diagrams are typically associated with use case realizations in the Logical View of the system under development. Sequence diagrams are sometimes called event diagrams, event scenarios, and timing diagrams.A sequence diagram shows, as parallel vertical lines (lifelines), different processes or objects that live simultaneously, and, as horizontal
arrows, the messages exchanged between them, in the order in which they occur. This allows the specification of simple runtime scenarios in a graphical manner.
If the lifeline is that of an object, it demonstrates a role. Note that leaving the instance name blank can represent anonymous and unnamed instances.
Messages, written with horizontal arrows with the message name written above them, display interaction. Solid arrows with full heads are asynchronous calls and dashed arrows with stick heads are return messages. This definition is true as of UML 2, considerably different from UML 1.x. a caller sends a synchronous message, it must wait until the message is done, such as invoking a subroutine. If a caller sends an asynchronous message, it can continue processing and doesn’t have to wait for a response. You see asynchronous calls in multithreaded applications and in message-oriented middleware. Activation boxes, or method-call boxes, are opaque rectangles drawn on top of lifelines to represent that processes are being performed in response to the message (ExecutionSpecifications in UML).
Objects calling methods on themselves use messages and add new activation boxes on top of any others to indicate a further level of processing.When an object is destroyed (removed from memory), an X is drawn on top of the lifeline, and the dashed line ceases to be drawn below it (this is not the case in the first example though). It should be the result of a message, either from the object itself, or another.

System under study:
Sahur Protocol is a single-file, browser-based 2D roguelike. The player fights through three biomes of rooms with Sahur as a companion, chooses a skill upgrade after every cleared room, defeats a biome boss, and finally confronts The AI Bubble. The whole run is driven by one animation loop whose mode variable moves between title, cutscene, play, choose, beats and end, while the run data is persisted to browser localStorage so that a run can be continued later.
Elements identified for the sequence diagram:
-  Actor - Player: supplies keyboard / touch-joystick input and menu clicks.
-  :GameUI (boundary) - the title screen, cutscene panels, upgrade overlays and end screens.
-  :GameCtrl (control) - the update / render loop and the mode manager of the run.
-  :RoomMgr (control) - room set-up, enemy spawning, boss spawning and clear detection.
-  :Enemy / :Boss / :Bubble (entity) - the opponents in a room, at a biome end, and in the finale.
-  :RunState (entity) - player, sahur, skills, biome, room and challenge data of the current run.
-  :SaveMgr (service) - saving, loading and clearing the run in browser localStorage.
-  Messages - solid arrows are synchronous calls and dashed arrows are return messages; loop and alt combined fragments express the room loop, the per-frame game loop and the win / lose branches.
A complete run contains a large number of interactions, so the sequence diagram is drawn as four continuous parts; each part begins exactly where the previous one ends.

Conclusion:
The behavioural view of Sahur Protocol was modelled as a UML sequence diagram in four parts. Drawing it made the control structure of the game explicit: :GameCtrl owns the mode of the run and delegates to :GameUI and :RoomMgr, each of which owns its own input and audio, while :RunState is the single entity that every object reads and writes and :SaveMgr is touched only at well-defined checkpoints - room start, room clear, biome change and the end of a run. The loop fragments show the two nested repetitions in the game, the per-room loop and the per-frame update loop, and the alt fragments capture the boss-defeated, next-biome and player-died branches. The diagram therefore records the time-ordered interaction between objects, which the static class and use-case views of the earlier experiments could not express.
